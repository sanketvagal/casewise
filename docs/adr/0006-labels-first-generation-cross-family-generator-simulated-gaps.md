# 6. Labels-first data generation, on a different model family, with simulated gaps

Date: 2026-11-18

Status: Accepted

## Context

Every number from issue 06 on is measured on synthetic tickets. A reviewer's first question will be whether that data is rigged in the system's favor. Three ways it could be:

- The ground truth is inferred from the ticket text after the text is written, so the labels inherit whatever the writer got wrong.
- The ticket writer shares a model family with triage, so the bot is graded on prose in its own style.
- The knowledge-base gaps that the insights report later "finds" are planted with knowledge of where they are.

## Decision

**Labels first, sampled in code.** `casewise generate` runs four steps, in this order:

1. A model writes the product spec: a summary and about 40 support topics across six fixed areas (scheduling, e-prescribing, lab orders and results, billing, patient portal, account admin). Validation requires 36 to 44 topics, unique kebab-case ids and at least 4 topics per area.
2. Code picks the 25 topics the initial knowledge base covers, with a seeded random draw that ignores topic volume. The 15 uncovered topics are the simulated gaps.
3. Code samples every ticket's labels with a seeded random generator: topic, requester role, practice size, plan tier, timestamp, tone, level of detail, safety situation, intent, answering article, must-escalate and escalation reason. The labels go to `data/labels.jsonl` before any ticket text exists.
4. A model writes each ticket's subject and body from a brief built from its labels, ten tickets per call. A model also writes one article per covered topic.

No model chooses or edits a label. The correct answer is known by construction.

- **Topic volume** is uneven (a seeded log-normal weight per topic) and the same in both splits, so a gap that costs deflection in weeks 1–2 also costs it in weeks 3–4.
- **Timestamps** fall in weekday working hours. Weeks 1–2 (from Monday 2026-10-05) and weeks 3–4 each get 200 tickets.
- **Safety situations.** 20% of each split (40 tickets) describes a safety-rule situation, 8 per rule. Prescription errors only occur on e-prescribing topics and billing disputes only on billing topics. Urgent-clinician tickets always come from a physician. The other rules can occur on any topic.
- **Must-escalate labels.** A rule situation's ticket gets `escalation_reason` equal to the rule id, even when its topic is covered. That follows the issue 04 fixtures. An uncovered topic with no rule situation gets `no_answer`.

**Rule tickets are written from a situation, not from the rule's phrases.** The writer is told what happened ("a prescription went to the wrong pharmacy"), never the keyword list in `safety_rules.yaml`. Every other ticket is told it is routine. Whether the keyword rules catch these tickets is therefore a finding, and `data/generation-report.md` counts it for each rule.

**The generator is Gemini**, on a different family from triage (gpt-oss-120b on Groq). It's `gemini-3.5-flash-lite`, the same model as the judge (ADR 5), with its own `generator_provider` and `generator_model` settings. The free tier allows about 500 Flash-Lite requests a day, and a full generation takes about 70 calls. Flash allows about 20 a day, which would spread one run over four days. Calls go through the gateway and its cache (ADR 2), so the committed `cache/` regenerates every file under `data/` byte for byte.

**Simulated gaps stay hidden.** Triage's intent labels stay the knowledge-base article ids plus `other`. A ticket on an uncovered topic is labeled `intent: other`, and its true `topic` is kept on the labeled ticket for scoring only. The uncovered topic ids are written only to `data/scoring/uncovered-topics.json`. Neither triage nor the insights report may read `topic`, `labels.jsonl`, `spec.json` or `data/scoring/`. The generation report gives the gap count but names no gap.

## Considered options

- **Labels generated by the model.** Rejected: the distribution is harder to control, a model can return labels that contradict each other, and it costs calls.
- **Intent = topic for every ticket.** Rejected: triage would need every topic id as a label, which hands it the names of the gaps.
- **Rule tickets that must use a rule phrase.** Rejected: the rules would catch every rule ticket by construction, making the safety numbers circular.
- **Covering the highest-volume topics first.** Rejected for now: real knowledge bases often do, but that would leave only rare topics as gaps, too small to cluster. Random coverage is simpler to defend.

## Consequences

- A prompt or seed change regenerates the world and starts a new baseline. Old cache entries still replay the old world.
- Generator and judge share a model (Flash-Lite), so the judge grades tickets and articles in its own style. Neither is the system under test, and issue 07's second-family re-judge measures the judge.
- The first run's report shows two things the triage evaluation will feel:
  - Of the 80 rule-situation tickets, 6 match no rule (2 patient data, 3 outage, 1 urgent clinician). The LLM checks are the only defense on those.
  - 99 of the 320 routine tickets match a rule anyway (60 `prescription_error`, mostly routine e-prescribing questions, and 33 `patient_data_exposure`). That caps deflection. Tuning the rules is a separate decision with its own baseline.
- Labels are fixed at generation. When issue 11 writes articles for closed gaps, intents on those topics must be relabeled from `topic`.
- The data under `data/` is not yet used by triage: `kb_dir` still points at the three hand-written articles that the issue 04 evaluation replays. Issue 06 switches it.
